# Ревью 008 — Медиа на диске сервера вместо S3
Дата: 2026-10-31 · Ревьюер: reviewer · План: `docs/ai/plans/008-local-storage.md`

## Вердикт: CHANGES REQUESTED

Одно блокирующее замечание: уборщик (`MediaSweeper`) удаляет **весь** старый контент, если сервер стартует с пустой или «не той» БД. Диск — единственная копия видео, а рекомендованный в README бэкап `rsync --delete` эту потерю повторит. Всё остальное по плану сделано аккуратно. S3 убран полностью. Загрузка идёт потоком на диск, тип определяется по сигнатуре, имя генерирует сервер. Guard → `DiskSpaceInterceptor` → multer выполняются в нужном порядке. Брошенные и прерванные загрузки чистит multer 2.5, а то, что он пропустил, удаляет уборщик.

## Что проверено и в порядке

- **Порядок выполнения.** `JwtAuthGuard` на классе срабатывает раньше всех interceptor-ов, так что аноним до диска не доходит (e2e «requires auth»). В Nest interceptor-ы из `@UseInterceptors(A, B)` вкладываются друг в друга: `intercept` у B (`FileInterceptor`, внутри которого multer) запускается только при подписке на `next.handle()` у A. `switchMap` после `ensureRoomFor` это обеспечивает, поэтому при ответе 507 multer не пишет на диск ни байта. Глобальных interceptor-ов нет.
- **Пути.** Итоговое имя — `randomUUID().<ext из сигнатуры>`, временное — `.upload-<uuid>`. Клиентское имя нигде не используется (e2e с `../../etc/passwd.mp4`). Статика `/media` отдаётся с `dotfiles: 'deny'`, `index: false`. `rename` выполняется в пределах той же папки, значит атомарен.
- **Временные файлы.** При ошибке типа или размера `store()` удаляет temp. Multer 2.5 при `LIMIT_FILE_SIZE`, `aborted`, `close` и ошибке потока удаляет и незавершённые файлы (`pendingFiles`). Что не удалилось (падение процесса), через 24 ч подберёт уборщик.
- **Лимиты.** `fileSize` = `MAX_VIDEO_MB`, `files: 1`, `fields: 0`. Картинке больше 10 МБ сервер отвечает 413 после записи и удаляет её. Значения env проверяются (`MAX_VIDEO_MB` 1..20480, `MIN_FREE_MB` ≥ 0).
- **Таймаут.** `app.getHttpServer()` до `listen` возвращает уже созданный http-сервер, а `requestTimeout` Node читает при каждой проверке соединений, так что 2 ч применяются. `headersTimeout` (60 с) не изменён.
- **Уборщик, безопасная часть.** Трогает только `^<uuid>\.(mp4|webm|jpg|png|webp)$` и `.upload-*`. Для симлинков и папок `lstat().isFile()` возвращает false, они пропускаются. Обхода вглубь нет. Ссылки читаются после листинга папки. Если SQL-запрос падает, исключение вылетает до первого `unlink` (ничего не удаляется) и пишется в лог. Таблиц с медиа ровно две: `projects.video_url/poster_url` и `settings.value` (профиль, шоурил, SEO). У `categories` URL-полей нет. Поиск подстрокой может дать только ложное «используется», то есть файл оставят, но не удалят. Таймер с `unref()` снимается при shutdown. Сид (`scripts/seed.ts`) Nest не поднимает, поэтому уборщик при нём не запускается.
- **Фронт.** Токен ставится только на запрос к своему API. При 401 выполняется разлогин. Сообщение об ошибке берётся из JSON, а если пришла HTML-страница прокси, показывается общий текст. Размер проверяется до отправки.

## Замечания

### Блокирующие

**1. Уборщик стирает весь контент, если БД пустая или подменена.** `backend/src/uploads/media-sweeper.ts:44-50, 65-68`
Последствие. Ошибка в `DATABASE_PATH` (относительный путь при другом `WorkingDirectory`, не тот volume в Docker при первом деплое, переезд на новый сервер с копированием папки `uploads` через `rsync -a`, которое сохраняет mtime) приводит к тому, что better-sqlite3 молча создаёт новую БД. Миграции проходят, `projects` и `settings` пустые, и `onApplicationBootstrap` сразу удаляет **все** медиа старше суток. Восстановление старого бэкапа БД стирает всё, что загрузили после него. Обнаружится это не сразу, а бэкап по рецепту из README (`rsync -a --delete`) к следующему запуску cron повторит удаление. Диск по условиям плана — единственная копия.
Исправить (достаточно одного, лучше двух):
- не удалять медиа (temp-файлы можно), если `SELECT COUNT(*) FROM projects` = 0;
- предохранитель: если удалить предстоит больше заметной доли медиа (например, > 20 % файлов или > 5 файлов за проход), только писать warning и ничего не удалять;
- добавить unit-тест «пустая БД → медиа не тронуты» и тест на предохранитель.

### Неблокирующие

**2. «Старше 24 ч» считается от mtime файла, а не от момента, когда на него перестали ссылаться.** `media-sweeper.ts:59`
Последствие. Если в работе заменить или убрать видео, загруженное больше суток назад, старый файл пропадёт при ближайшем проходе, то есть в течение часа, и откатиться будет нельзя. Тексты в README и в админке («старше суток») наводят на мысль, что сутки дают после удаления. Обратная ситуация: файл загрузили, форму не сохраняли больше суток, потом сохранили — работа будет ссылаться на уже удалённый файл (404).
Исправить. Хранить «кандидатов» с отметкой времени, когда файл впервые оказался без ссылок (например, `touch`/таблица `orphans`), и удалять через 24 ч после этого. Либо поправить формулировку в README и в админке. При сохранении работы стоит проверять, что `/media/…`-файл существует (400 вместо битой ссылки).

**3. Без `Content-Length` проверка места фактически не выполняется.** `backend/src/uploads/uploads.controller.ts:26`
Последствие. При chunked-запросе `declared = 0`. Тогда проверяется только, что сейчас свободно ≥ `MIN_FREE_MB`, а дальше multer может записать до `MAX_VIDEO_MB` и при значениях по умолчанию (2048/2048) съесть почти весь резерв. Две параллельные загрузки тоже проходят проверку одновременно. Браузерный XHR с `FormData` всегда шлёт длину, так что риск низкий.
Исправить. Если `Content-Length` нет, отвечать 411 или считать `incoming = maxVideoBytes`.

**4. В e2e нет тестов на 413 и на 507 до записи, хотя план их требует.** `backend/test/app.e2e-spec.ts:218-282`
Последствие. Главное свойство («507 до записи на диск») держится только на порядке декораторов, и рефакторинг может его незаметно сломать. Unit-тест покрывает только `ensureFreeSpace`. Не проверено и то, что после `LIMIT_FILE_SIZE` не остаётся temp-файла.
Исправить. Отдельный `describe` с `MAX_VIDEO_MB=1` (тело > 1 МБ → 413, в папке нет `.upload-*`) и с огромным `MIN_FREE_MB` или подменённым `statfs` (→ 507, в папке пусто).

**5. Фронт сравнивает размер файла с `freeBytes` без учёта резерва.** `src/lib/adminApi.ts:165`
Последствие. Файл, который «влезает» в свободное место, но залезает в `MIN_FREE_MB`, всё равно уходит на сервер. Сервер сразу отвечает 507, но тело Node дочитывает и выбрасывает, так что браузер может гнать гигабайты впустую или показать «соединение оборвалось» вместо понятного текста.
Исправить. Добавить в `usage` `minFreeBytes` (или отдавать `freeBytes` за вычетом резерва) и сравнивать с ним. Контракт в плане обновить.

**6. Бэкап `rsync --delete` из README копирует ошибки, а не защищает от них.** `backend/README.md` («Бэкап»)
Последствие. Ошибочное удаление (уборщик, человек) к следующей ночи повторится в копии.
Исправить. Рекомендовать версии: снапшоты хостера, `rsync --backup --backup-dir=…/$(date +%F)` или restic/borg с ротацией. Отдельно напомнить: при восстановлении БД из старого бэкапа файлы, загруженные позже, уборщик удалит.

**7. `requestTimeout` 2 ч действует на все запросы, а не только на загрузку.** `backend/src/main.ts:11`
Последствие. Медленным телом любой запрос можно держать до 2 ч ещё до авторизации (slowloris по телу). За Caddy это сглаживается, без прокси — нет.
Исправить. Описать в README, что API без прокси не выставлять, либо настроить таймауты на прокси (в Caddy — `servers { timeouts { read_body … } }`, отдельно для `/api/admin/uploads`).

**8. Устаревший комментарий про S3.** `src/lib/api.ts:24-25` («local storage driver… S3 URLs are absolute»)
Исправить. Переписать: `/media/*` лежит на API-хосте, абсолютные `https://` URL (внешние или старые) отдаются как есть.

**9. Мелочи.**
- `WorksAdmin.tsx`: занятое место считается один раз при загрузке списка и после загрузки файла не обновляется.
- `uploads.service.ts:84-89`: `usage()` делает `stat` по одному файлу на каждый запрос. Для сотен файлов это нормально, для десятков тысяч станет медленно.
- `app.e2e-spec.ts` «counts stored files» зависит от порядка тестов (ровно 2 файла из предыдущих `it`). Допустимо, но хрупко.
- `MIN_FREE_MB` без `@Max`, опечатка в значении (например, лишний ноль) даст 507 на любую загрузку. Сообщение 507 при этом понятное, так что некритично.
